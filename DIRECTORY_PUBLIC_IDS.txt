Directory public IDs: rollout state and checks

Current state: code and migration are prepared. This file does not attest to a deployed migration, a backfill, or a working Vessel Directory API. The current runner cannot resolve its configured PostgreSQL host or public internet hosts. Do not deploy API code that selects public_id until the migration and backfill have passed in the target environment.

Canonical identities
- Imported vessel: magicport_vessel_directory.id/source_key, VSL public ID.
- Managed vessel: vessels.id, MVS public ID. A verified master_vessel_id link makes the imported VSL ID the displayed canonical reference in both views. The MVS reference remains stored and resolves to that imported record through the foreign key.
- Port: ports.id, PRT public ID.
- Company: maritime_directory_entities.id, COM public ID reused across its categories.
- Consultant: experts.id; existing numeric nexaport_id is retained. Records without one receive an EXP public ID. Surveyor views of that expert reuse it.
- Flag inspector, accredited inspector, appointed surveyor: FLI, ACI, APS IDs on their respective source tables.
- Flag state and accreditation scheme: FLG and SCH IDs.

Each new ID has 128 random bits encoded as 32 uppercase hexadecimal characters. Prefixes are disjoint; partial unique indexes prevent duplicates within each table. Insert/update triggers assign new IDs and reject changes to issued IDs. Existing primary and foreign keys remain intact. Vessel imports use source_key/IMO conflict handling and do not update public_id.

Controlled rollout order
1. Confirm the target database, deployment commit, connection, and table/column inventory. The previously issued expert-ID migration, sql/nexaport_public_ids_001.sql, is a prerequisite.
2. In an isolated PostgreSQL database with representative data, run psql -v ON_ERROR_STOP=1 -f sql/directory_public_ids_001.sql. This file must run with autocommit enabled because its indexes are built concurrently after the schema transaction. Check every index is valid. Do not run it inside an outer transaction.
3. In that isolated database, run node scripts/backfillDirectoryPublicIds.js --apply twice. The second run must report zero newly updated rows, full coverage, and distinct IDs equal to record counts. Exercise inserts, edits, imports, aliases, list/count, details, and permissions.
4. After explicit production rollout authorization, repeat the migration and backfill against the verified target. The backfill commits up to 1,000 rows per batch and is rerunnable. Run sql/directory_public_ids_verify.sql with the API database role and record actual counts, including imported vessels.
5. Deploy backend and frontend only after the target migration is verified. Use a Super Admin session to verify GET /api/vessel-directory?page=1&limit=30, pagination, sorting, details, ID search, and client records. Check server logs for directory-page versus directory-count PostgreSQL codes.

Read-only incident diagnosis
Run node scripts/diagnoseVesselDirectory.js using the deployed backend's authorized database configuration. It tests the five vessel tables and columns, counts existing rows, and runs the actual page and count SQL in separate read-only transactions. It prints only stage, SQLSTATE code, table/column names, counts, and schema metadata. No data is changed.
